## Trigger Conditions

Initiate rollback immediately if **any** of the following is observed within 30 minutes of blue-green switchover:

| Signal | Threshold | Monitor |
|--------|-----------|---------|
| HTTP 5xx error rate on `/api/v1/mock-sessions` | > 5% for > 5 consecutive minutes | CloudWatch ALB `HTTPCode_Target_5XX_Count` |
| HTTP 5xx error rate on `/api/v1/bookings` | > 2% for > 5 consecutive minutes | CloudWatch ALB |
| Health check failing on ECS tasks | ≥ 1 task failing `/health` for > 3 minutes | ECS service health check |
| BullMQ scoring queue depth | > 500 jobs pending for > 10 minutes | CloudWatch custom metric `ScoringQueueDepth` |
| WebRTC ICE negotiation failure rate | > 30% of new sessions for > 5 minutes | Application metric `webrtc.ice.failure_rate` |
| P95 API latency | > 2000ms on any endpoint for > 5 minutes | CloudWatch ALB `TargetResponseTime` P95 |
| Database connection errors | > 10 errors/minute | Application log filter `"db connection"` |

**Do not wait for multiple signals.** Any single sustained trigger above warrants immediate rollback.

## Rollback Steps

Execute in order. Do not skip steps.

### Step 1 — Notify On-Call

```
PagerDuty incident: "v1.1.0 rollback initiated"
Severity: SEV-1
Channel: #incidents
Message: "Rolling back v1.1.0 to v1.0.x due to [TRIGGER]. ETA: 10 minutes. On-call: [NAME]"
```

### Step 2 — Freeze Deployments

In AWS CodePipeline (or CI system), disable auto-deploy to prevent a new blue deployment from starting during rollback:

```bash
aws codepipeline disable-stage-transition \
  --pipeline-name interview-prep-prod \
  --stage-name Deploy \
  --transition-type Inbound \
  --reason "Rollback in progress — v1.1.0"
```

### Step 3 — Switch ALB Target Group Back to Green

Identify the current listener ARN and the green target group ARN from SSM Parameter Store:

```bash
LISTENER_ARN=$(aws ssm get-parameter \
  --name /interview-prep/prod/alb/listener-arn \
  --query "Parameter.Value" --output text)

GREEN_TG_ARN=$(aws ssm get-parameter \
  --name /interview-prep/prod/alb/green-target-group-arn \
  --query "Parameter.Value" --output text)

aws elbv2 modify-listener \
  --listener-arn "$LISTENER_ARN" \
  --default-actions Type=forward,TargetGroupArn="$GREEN_TG_ARN"
```

### Step 4 — Verify Green Health

```bash
# Wait 30 seconds for ALB to drain blue connections
sleep 30

# Confirm green tasks are serving traffic
curl -sf https://api.platform.com/health | jq .
# Expected: {"status":"ok","version":"1.0.x"}

curl -sf https://api.platform.com/ready | jq .
# Expected: {"status":"ready"}
```

If green returns non-200, escalate immediately to `senior_architect_agent` — do NOT proceed.

### Step 5 — Scale Down Blue ECS Tasks (v1.1.0)

```bash
aws ecs update-service \
  --cluster interview-prep-prod \
  --service api-blue \
  --desired-count 0
```

### Step 6 — Database Rollback (only if Phase 2 migrations were applied)

> **Check first:** Query `schema_migrations` table to confirm whether Phase 2 migrations ran:
> ```sql
> SELECT version FROM schema_migrations ORDER BY applied_at DESC LIMIT 5;
> ```

If Phase 2 migrations (`0002_*` through `000N_*`) were applied, run the down scripts in **reverse order**:

```bash
# From the backend directory:
npm run db:migrate:down -- --to 0001_initial

# Verify: confirm Phase 2 tables are gone
psql $DATABASE_URL -c "\dt" | grep -E "expert|booking|rubric|playbook"
# Expected: no rows returned
```

> **Warning:** Rolling back migrations is destructive if users have created bookings or expert profiles. Coordinate with `db_architect_agent` before executing migration rollback. If any Phase 2 user data exists, snapshot the database first:
> ```bash
> aws rds create-db-snapshot \
>   --db-instance-identifier interview-prep-prod \
>   --db-snapshot-identifier pre-rollback-v1.1.0-$(date +%Y%m%d%H%M%S)
> ```

### Step 7 — Drain BullMQ Queue (if scoring jobs are stuck)

If the scoring queue has stuck jobs referencing Phase 2 job types:

```bash
# Connect to Redis and flush Phase 2 job types only
redis-cli -u "$REDIS_URL" LRANGE bull:scoring:wait 0 -1
# Inspect — remove Phase 2 job types if present using LREM
```

Do not flush the entire queue — Phase 1 scoring jobs may still be valid.

### Step 8 — Re-Enable Deployments

After confirming green is stable for 15 minutes:

```bash
aws codepipeline enable-stage-transition \
  --pipeline-name interview-prep-prod \
  --stage-name Deploy \
  --transition-type Inbound
```

### Step 9 — Post-Rollback Notification

Send to Slack `#incidents` and `#engineering`:

```
RESOLVED: v1.1.0 rollback complete.
Green (v1.0.x) is serving 100% of traffic.
Health checks: passing.
Next steps: post-mortem scheduled within 48h.
Incident owner: [NAME]
```

## Post-Rollback Actions (within 48 hours)

1. Open post-mortem issue in GitHub with label `incident` and `phase-2`
2. Root-cause analysis: attach CloudWatch logs, error traces, and queue metrics from the failure window
3. Fix the root cause in the codebase before re-attempting Phase 2 deployment
4. Re-run full 7-gate checklist before scheduling next switchover attempt
5. Update this runbook if any step was unclear or ineffective during the incident
