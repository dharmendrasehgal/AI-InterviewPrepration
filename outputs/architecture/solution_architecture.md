## 1. Architecture Principles

| # | Principle | Rationale |
|---|-----------|-----------|
| 1 | **Monolith-first, modular boundaries** | Start with a modular monolith for MVP speed; boundaries are drawn so services can be extracted in Phase 3 without data coupling |
| 2 | **AI-native design** | AI is a first-class citizen — question generation, scoring, and personalization are core flows, not bolt-ons |
| 3 | **Privacy by design** | Consent, encryption, and data retention are enforced at the platform layer — not left to individual features |
| 4 | **Async-first for media** | Recording upload, STT transcription, and AI scoring are always asynchronous — the user is never blocked waiting for processing |
| 5 | **Accessibility as a constraint** | WCAG 2.1 AA is a build gate, not a post-launch audit |
| 6 | **Progressive enhancement** | Core flows (question browsing, profile setup) function without JS; AI session requires JS and camera/mic |

## 3. Technology Stack

### 3.1 Frontend

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| Framework | **Next.js 14** (App Router) | SSR for SEO, built-in PWA support, React Server Components reduce JS bundle |
| Language | **TypeScript** | Type safety across full stack; shared types with backend via tRPC or OpenAPI codegen |
| Styling | **Tailwind CSS** + **shadcn/ui** | Accessible component primitives; rapid consistent UI; WCAG-compliant components |
| State Management | **Zustand** (client) + **TanStack Query** (server state) | Lightweight; avoids Redux boilerplate for this scale |
| Video/WebRTC | **MediaRecorder API** + **RTCPeerConnection** (native browser) | No SDK dependency for recording; standard WebRTC for live sessions |
| PWA | **next-pwa** | Service worker, offline caching of Question Bank and Playbooks |
| Testing | **Playwright** (E2E) + **Vitest** (unit) | Playwright captures full browser flows including media |

### 3.2 Backend

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| Runtime | **Node.js 22 LTS** | Same language as frontend (TypeScript); excellent async I/O for streaming |
| Framework | **Fastify** | 2× throughput of Express; built-in schema validation; plugin ecosystem |
| API Style | **REST** (public API) + **WebSocket** (real-time notifications, signaling) | REST is standard and cacheable; WS for low-latency events |
| Authentication | **JWT** (access token 15min) + **Refresh token rotation** + **Google OAuth 2.0** | Stateless, horizontally scalable; OAuth for social login |
| Job Queue | **BullMQ** (Redis-backed) | Reliable async processing for STT, scoring, email, and recording upload jobs |
| WebRTC Signaling | **mediasoup** (SFU) | Scalable Selective Forwarding Unit; handles N-party sessions and recording relay |

### 3.3 AI & Speech

| Component | Technology | Rationale |
|-----------|-----------|-----------|
| Question Generation | **Anthropic Claude API** (claude-sonnet-4-6) | Best-in-class instruction following; adaptive question generation based on profile |
| Answer Evaluation | **Anthropic Claude API** | Keyword relevance scoring, answer quality assessment via structured prompts |
| Speech-to-Text | **OpenAI Whisper** (self-hosted on GPU instance) | Highest accuracy for English; no per-minute API cost at scale; data stays in-house |
| Filler Word Detection | **Custom regex + NLP post-processor** on Whisper transcript | Simple, deterministic, no external API needed |
| Speech Rate | **Word count / duration** from Whisper word-level timestamps | Whisper returns word-level timestamps natively |

### 3.4 Data

| Store | Technology | Use Case |
|-------|-----------|---------|
| Primary DB | **PostgreSQL 16** (AWS RDS Multi-AZ) | Users, questions, sessions, scores, bookings, rubrics |
| Cache | **Redis 7** (AWS ElastiCache) | Session tokens, rate limiting counters, job queues (BullMQ), search result caching |
| Object Storage | **AWS S3** (with server-side AES-256 encryption) | Session recordings (video/audio), resumes, transcripts, exported PDFs |
| Search | **PostgreSQL full-text search** (pg_trgm + tsvector) | Sufficient for MVP; migrate to OpenSearch in Phase 3 if needed |
| CDN | **AWS CloudFront** | Static assets, video delivery, transcript downloads |

### 3.5 Infrastructure

| Component | Technology | Notes |
|-----------|-----------|-------|
| Cloud Provider | **AWS** | Broadest compliance certifications (SOC2, GDPR tooling); managed RDS, S3, CloudFront |
| Compute | **AWS ECS (Fargate)** | Serverless containers; auto-scaling; no EC2 management overhead for MVP |
| Container | **Docker** | Consistent build environments; same image runs locally and in prod |
| IaC | **Terraform** | Reproducible infrastructure; enables staging/prod parity |
| CI/CD | **GitHub Actions** | Lint → Test → Build → Deploy pipeline per environment |
| Secrets | **AWS Secrets Manager** | API keys (Anthropic, Whisper, SendGrid) never in codebase |
| Monitoring | **AWS CloudWatch** + **Sentry** | Infrastructure metrics + application error tracking |

## 5. Security Architecture

### 5.1 Authentication & Authorization

```
Request ──▶ WAF ──▶ ALB ──▶ JWT Middleware ──▶ RBAC Guard ──▶ Handler
                              │                    │
                              ▼                    ▼
                         Verify token          Check role
                         (RS256 public key)    (Candidate/Expert/Admin)
                         Check expiry (15min)  Reject if insufficient
                         Validate user_id      permission
```

- Access tokens: RS256 signed JWT, 15-minute expiry
- Refresh tokens: opaque, stored in `HttpOnly SameSite=Strict` cookie, 30-day expiry with rotation on use
- Admin tokens: separate `admin` claim scope; all admin endpoints check for this scope explicitly

### 5.2 Data Encryption

| Data Type | At Rest | In Transit |
|-----------|---------|-----------|
| Session recordings (S3) | AES-256 (SSE-S3) | TLS 1.3 (CloudFront → S3) |
| PII in PostgreSQL | pgcrypto for sensitive fields (email, full name) | TLS 1.3 (app → RDS) |
| Resume files (S3) | AES-256 (SSE-S3) | TLS 1.3 |
| Redis (tokens, queues) | In-memory only; no PII stored | TLS 1.3 (app → ElastiCache) |

### 5.3 Consent & Audit Logging

- Every recording consent event writes to an immutable `consent_log` table: `(user_id, session_id, consent_type, accepted_at, ip_address, user_agent)`
- All admin actions write to an immutable `audit_log` table retained for 12 months
- Logs are shipped to AWS CloudWatch with a 12-month retention policy
- `audit_log` and `consent_log` tables have INSERT-only permissions at the application role level (no UPDATE, no DELETE)

## 6. Scalability Architecture

### Phase 1 Sizing (MVP)

| Component | Initial Sizing | Auto-scale Trigger |
|-----------|---------------|-------------------|
| API (Fargate) | 2 tasks × 0.5 vCPU / 1GB | CPU > 70% → scale up; max 20 tasks |
| WebSocket Server | 2 tasks × 0.5 vCPU / 1GB | Connections > 500/task → scale |
| Signaling Server (mediasoup) | 2 tasks × 1 vCPU / 2GB | Active rooms > 50/task → scale |
| Whisper STT (GPU) | 1 GPU instance (g4dn.xlarge) | Queue depth > 10 → scale |
| BullMQ Workers | 4 tasks (CPU) | Queue depth > 20/worker → scale |
| PostgreSQL (RDS) | db.t3.medium Multi-AZ | Manual upgrade to db.r6g.large at Phase 2 |
| Redis (ElastiCache) | cache.t3.small | Manual upgrade at Phase 2 |

### Async Queue Priority Lanes

```
High Priority:   STT transcription + AI scoring  (user is waiting for report)
Medium Priority: Email notifications              (time-sensitive but not blocking)
Low Priority:    Recording upload cleanup         (background maintenance)
```
