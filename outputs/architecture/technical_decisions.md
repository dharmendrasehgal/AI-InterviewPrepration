## ADR-001: Modular Monolith over Microservices for Phase 1

**Status:** Accepted  
**Date:** 2026-05-26

### Context
The team is building a new platform from scratch. We must choose between a microservices architecture (maximum operational flexibility) and a monolith (faster iteration).

### Decision
Start with a **modular monolith** — a single deployable unit with clearly bounded internal modules (Auth, Content, Session, Scoring, Notification, Admin). Module boundaries are enforced by TypeScript barrel exports and no cross-module direct DB access (each module owns its DB tables and exposes a service interface).

### Consequences
- **Positive:** Faster development velocity in Phase 1; single deployment; easier debugging; no distributed transaction complexity.
- **Positive:** Module boundaries mean extracting a service in Phase 3 requires only adding a network boundary around an existing module — not a re-architecture.
- **Negative:** All modules share the same process — a memory leak in Scoring affects Auth. Mitigated by health checks and restart policies.
- **Negative:** Whisper STT requires GPU compute — this module is extracted to a standalone worker from day one (not in the monolith).

## ADR-002: Next.js 14 (App Router) as Frontend Framework

**Status:** Accepted  
**Date:** 2026-05-26

### Context
We need a React-based framework that supports SSR (for SEO on Question Bank and Playbook pages), PWA, and TypeScript natively.

### Decision
Use **Next.js 14** with the App Router (React Server Components).

### Rationale
- Server Components reduce JS bundle on Question Bank and Playbook pages (no client hydration needed for static content).
- Built-in image optimization, code splitting, and prefetching.
- `next-pwa` adds service worker and offline caching with minimal configuration.
- API Routes support simple backend-for-frontend (BFF) patterns where needed.

### Alternatives Rejected
- **Remix:** Less ecosystem maturity; smaller community for enterprise patterns.
- **SvelteKit:** Excellent performance but team TypeScript/React expertise is higher for React.

## ADR-003: Fastify over Express or NestJS

**Status:** Accepted  
**Date:** 2026-05-26

### Context
Node.js HTTP framework choice for the REST API backend.

### Decision
Use **Fastify** with TypeScript.

### Rationale
- 2× throughput vs Express in benchmarks for I/O-bound workloads.
- Built-in JSON Schema validation via Ajv — request/response validation without an extra library.
- Native TypeScript support; excellent plugin ecosystem (JWT, CORS, rate limiting, multipart).
- Structured logging with Pino out of the box (JSON logs for CloudWatch).

### Alternatives Rejected
- **Express:** Slower; no built-in validation; less structured logging.
- **NestJS:** Excellent for large teams but adds significant abstraction overhead for a modular monolith that doesn't need an IoC container.

## ADR-004: Anthropic Claude API for AI Question Generation and Scoring

**Status:** Accepted  
**Date:** 2026-05-26

### Context
The platform needs AI for: (a) adaptive mock interview question generation personalized to candidate profile, (b) keyword relevance scoring of candidate answers.

### Decision
Use **Anthropic Claude API** (claude-sonnet-4-6 model) for both generation and evaluation.

### Rationale
- Superior instruction-following for structured output (question + rubric + scoring criteria).
- Claude's extended context window handles full resume + job description + question history in a single prompt.
- Anthropic's data processing agreement is compatible with GDPR requirements.
- Structured output (JSON mode) ensures reliable parsing of scoring responses.

### Implementation Notes
- Enable **prompt caching** on static system prompts (question bank categories, scoring rubrics) to reduce latency and cost by ~80% on repeated calls.
- Use a thin abstraction layer (`AIService`) so the provider can be swapped without changing business logic.

### Alternatives Rejected
- **OpenAI GPT-4o:** Strong alternative; rejected to avoid vendor overlap with Whisper (two OpenAI dependencies is a concentration risk).
- **Google Gemini:** API consistency and structured output reliability are behind Claude for this use case at time of decision.

## ADR-005: Whisper (Self-Hosted) over Cloud STT APIs

**Status:** Accepted  
**Date:** 2026-05-26

### Context
Speech-to-Text is required for all AI mock interview sessions. Key requirements: high accuracy, word-level timestamps (for WPM calculation), data privacy (no audio sent to third parties without DPA), cost at scale.

### Decision
Self-host **OpenAI Whisper large-v3** on a dedicated GPU instance (AWS g4dn.xlarge).

### Rationale
- Word-level timestamps are native — required for WPM and pacing marker features.
- Audio never leaves our AWS environment — strongest GDPR/CCPA posture.
- At 500 sessions/day × 15 minutes average, Google STT would cost ~$1,350/month. Whisper on g4dn.xlarge is ~$530/month fixed.
- Whisper large-v3 achieves ~2.7% WER on clean English speech — exceeds our 85% accuracy target.

### Consequences
- We own the GPU instance — must manage availability and patching.
- GPU instance is a single point of failure for STT. Mitigated by: async queue (sessions tolerate up to 5-minute scoring delay), and a fallback to Google STT API if Whisper queue depth exceeds 50 jobs.

### Alternatives Rejected
- **Google Speech-to-Text:** No word-level timestamps in v1 API; higher per-minute cost at scale; audio leaves our infrastructure.
- **AWS Transcribe:** Word-level timestamps available but 20–30% higher cost than Google; slower turn-around on async jobs.

## ADR-006: mediasoup (SFU) for WebRTC Live Sessions

**Status:** Accepted  
**Date:** 2026-05-26

### Context
Live human-led mock interviews require real-time video/audio between candidate and expert, plus server-side recording.

### Decision
Use **mediasoup** as a Selective Forwarding Unit (SFU) for WebRTC signaling and media routing.

### Rationale
- SFU architecture means media flows through the server — enables server-side recording without requiring client-side recording relay.
- mediasoup is open-source, runs on our infrastructure (no per-minute SDK cost like Daily.co or Zoom).
- Supports up to 500 concurrent rooms on 2 × 4 vCPU instances (sufficient for Phase 1 and 2 targets).
- Server-side recording to S3 is a first-class feature.

### Alternatives Rejected
- **Zoom SDK:** ~$0.003/participant-minute at scale; vendor lock-in; adds legal complexity around Zoom's own data retention.
- **Daily.co / LiveKit:** Managed SaaS; excellent DX but $0.004/participant-minute and data leaves our infrastructure.
- **Pure P2P WebRTC:** Cannot record server-side; no relay through NAT for all users; no scalability beyond 2-party sessions.

## ADR-007: PostgreSQL as Primary Database

**Status:** Accepted  
**Date:** 2026-05-26

### Context
Primary persistent store for users, questions, sessions, scores, bookings, rubrics, and consent logs.

### Decision
Use **PostgreSQL 16** on AWS RDS Multi-AZ.

### Rationale
- Relational model fits the domain perfectly: Questions → Answers → Sessions → Scores → Users all have well-defined foreign key relationships.
- `pg_trgm` extension enables full-text search sufficient for Phase 1 (avoids an Elasticsearch cluster until scale justifies it).
- `pgcrypto` enables column-level encryption for PII fields.
- INSERT-only tables for consent and audit logs are enforceable via PostgreSQL row-level security.
- AWS RDS Multi-AZ provides automated failover, point-in-time recovery, and daily snapshots.

### Alternatives Rejected
- **MongoDB:** Document model doesn't naturally fit the relational question/session/score data; complex joins become application-level.
- **DynamoDB:** Excellent at scale but single-table design is complex to evolve; full-text search requires OpenSearch anyway.

## ADR-008: BullMQ over AWS SQS for Job Queue

**Status:** Accepted  
**Date:** 2026-05-26

### Context
Async processing is required for: STT transcription, AI scoring, email dispatch, and recording upload cleanup.

### Decision
Use **BullMQ** (Redis-backed) for the job queue.

### Rationale
- BullMQ runs on the same Redis instance already used for caching and session storage — no additional infrastructure.
- Priority queues, delayed jobs, and retry-with-backoff are built-in.
- Job progress updates can be pushed to the WebSocket server directly from a worker (for real-time "Your score is ready" notification).
- Admin UI (Bull Board) provides visibility into queue health without additional tooling.

### Consequences
- Redis becomes a higher-criticality dependency (also powers job queue). Mitigated by ElastiCache Multi-AZ replication.

### Alternatives Rejected
- **AWS SQS:** No priority queues; no real-time job progress; would require additional infrastructure.
- **RabbitMQ:** Operationally heavier than Redis for this scale; no built-in UI without plugins.
