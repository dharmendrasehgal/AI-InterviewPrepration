## Risk Register

### RISK-01: Whisper STT GPU Instance — Single Point of Failure

| Field | Detail |
|-------|--------|
| **Category** | Technical / Infrastructure |
| **Likelihood** | 3 (GPU instances can be terminated, spot interruptions) |
| **Impact** | 4 (AI score reports blocked; users wait indefinitely) |
| **Score** | 12 — High |
| **Description** | If the Whisper GPU instance becomes unavailable, the STT transcription queue halts. No transcription = no AI score report. Users who have just completed a session will receive no feedback. |
| **Mitigation** | 1. Run Whisper on On-Demand instance (not Spot) for reliability. 2. Configure BullMQ dead-letter queue — jobs retry with exponential backoff for up to 1 hour. 3. Fallback: if Whisper queue depth > 50 or instance health check fails, route new jobs to Google STT API (higher cost, but maintains availability). 4. Alert on-call when Whisper instance is unreachable for > 2 minutes. |
| **Residual Risk** | Score 6 — Medium (with fallback to Google STT) |
| **Owner** | DevOps Architect |

### RISK-02: WebRTC NAT Traversal Failures in Live Sessions

| Field | Detail |
|-------|--------|
| **Category** | Technical / User Experience |
| **Likelihood** | 3 (Corporate firewalls, symmetric NAT, strict enterprise networks) |
| **Impact** | 4 (Live session completely unusable for affected user) |
| **Score** | 12 — High |
| **Description** | WebRTC P2P connections can fail for users behind symmetric NAT or strict corporate firewalls. mediasoup's SFU mitigates most cases (media relayed through server), but TURN relay is required as a fallback. Without TURN, an estimated 10–15% of sessions may fail to connect. |
| **Mitigation** | 1. Deploy Coturn TURN server in the same AWS region as mediasoup (low latency relay). 2. Configure TURN credentials with short-lived tokens (1-hour HMAC-based credentials). 3. Implement pre-session connectivity check ("Test your connection" wizard before first session). 4. Add fallback Zoom link generation for bookings where WebRTC fails (Phase 2 safety net). |
| **Residual Risk** | Score 4 — Low |
| **Owner** | Backend Architect |

### RISK-03: Anthropic Claude API — Rate Limits or Outage

| Field | Detail |
|-------|--------|
| **Category** | Technical / External Dependency |
| **Likelihood** | 2 (Anthropic has high availability SLA, but outages occur) |
| **Impact** | 4 (AI mock interview sessions cannot generate questions; scoring unavailable) |
| **Score** | 8 — Medium |
| **Description** | The AI mock interview flow depends on the Claude API for question generation and answer scoring. If the API is rate-limited or unavailable, sessions cannot start or scoring is delayed. |
| **Mitigation** | 1. Enable prompt caching on system prompts to reduce API calls by ~80% (reduces rate limit exposure). 2. Pre-generate a pool of 50 cached question sets per track/level combination daily — sessions draw from this pool if the API is unavailable. 3. Implement circuit breaker: if Claude API returns 3 consecutive errors, switch to cached questions and queue scoring for retry. 4. Monitor Anthropic status page; alert on-call on first API error spike. |
| **Residual Risk** | Score 4 — Low |
| **Owner** | Backend Architect |

### RISK-04: GDPR/CCPA Non-Compliance — Recording Consent Gaps

| Field | Detail |
|-------|--------|
| **Category** | Legal / Compliance |
| **Likelihood** | 2 (If consent flow is misimplemented or logging fails) |
| **Impact** | 5 (Regulatory fines up to 4% of annual turnover; reputational damage) |
| **Score** | 10 — High |
| **Description** | Recording personal video/audio without explicit consent is a GDPR violation. If the consent dialog is skipped (e.g., a race condition in the session start flow), or if consent is not logged correctly, the platform is exposed to regulatory action. |
| **Mitigation** | 1. Recording only begins server-side after the API receives confirmed consent from both parties — the session start API endpoint is the only gate for recording activation. 2. Consent logging is synchronous (blocking) — if consent write fails, session does not start. 3. Legal review of consent dialog wording before Beta launch. 4. Automated test in CI that verifies recording cannot begin without a consent record in the DB. 5. GDPR Data Protection Impact Assessment (DPIA) completed before Phase 1 GA. |
| **Residual Risk** | Score 4 — Low |
| **Owner** | Senior Architect + Legal |

### RISK-05: Resume Parsing Accuracy — Personalization Quality

| Field | Detail |
|-------|--------|
| **Category** | Product / UX |
| **Likelihood** | 4 (Resume formats are extremely varied — PDF with columns, tables, graphics) |
| **Impact** | 3 (Poor personalization; candidate gets generic questions despite uploading resume) |
| **Score** | 12 — High |
| **Description** | Resume parsing is used to personalize AI question generation. If parsing fails or extracts incorrect data (common with multi-column PDFs, scanned documents, or non-English resumes), the AI receives garbage input and generates poor questions. This degrades the core value proposition. |
| **Mitigation** | 1. Use Claude API for resume parsing (better at extracting structured data from unstructured PDFs than regex-based parsers). 2. After parsing, show candidate a confirmation screen: "We extracted these skills and your current role — is this correct?" Candidate can edit before proceeding. 3. If parsing confidence is low (< 70% of expected fields extracted), fall back to profile questionnaire form rather than silently using bad data. 4. Log parsing failures for quality review. |
| **Residual Risk** | Score 6 — Medium |
| **Owner** | Backend Architect |

### RISK-06: Expert Marketplace — Insufficient Supply at Phase 2 Launch

| Field | Detail |
|-------|--------|
| **Category** | Business / Product |
| **Likelihood** | 3 (Expert onboarding is manual and takes time to scale) |
| **Impact** | 4 (Phase 2 launch with < 50 experts = long booking wait times; poor candidate experience) |
| **Score** | 12 — High |
| **Description** | The Phase 2 exit criteria require ≥ 50 active experts at launch. Expert recruitment and verification is a manual process. If expert supply is insufficient at launch, candidates cannot book sessions and the live interview feature is effectively unusable. |
| **Mitigation** | 1. Begin expert recruitment and onboarding during Phase 1 development (not after Phase 2 ships). 2. Build the expert registration and admin approval flow in Phase 1 backlog as P2 items so expert applications can be processed early. 3. Define a minimum viable expert roster of 50 as a hard gate for Phase 2 GA launch. 4. Consider launching Phase 2 in a limited beta with 20 experts and a waitlist to manage demand while supply grows. |
| **Residual Risk** | Score 6 — Medium |
| **Owner** | Product Manager + Operations |

### RISK-07: PostgreSQL Performance Under Full-Text Search Load

| Field | Detail |
|-------|--------|
| **Category** | Technical / Scalability |
| **Likelihood** | 2 (Unlikely in Phase 1 with < 1,000 questions; likely in Phase 3 with > 5,000 questions) |
| **Impact** | 3 (Search latency exceeds 500ms NFR; degraded UX) |
| **Score** | 6 — Medium |
| **Description** | PostgreSQL `pg_trgm` full-text search is sufficient for Phase 1 content volume but may degrade as the question bank grows beyond 5,000 questions and concurrent search traffic increases. |
| **Mitigation** | 1. Index all search columns with `GIN` indexes using `tsvector` from Phase 1 (correct indexing avoids most issues). 2. Cache popular search results in Redis (TTL 5 minutes). 3. Monitor search query latency via `pg_stat_statements`. 4. Add OpenSearch to Phase 3 roadmap as a planned upgrade — migration path is pre-designed (don't couple application code to PostgreSQL FTS specifics). |
| **Residual Risk** | Score 3 — Low |
| **Owner** | DB Architect |

### RISK-08: Browser Compatibility — MediaRecorder API

| Field | Detail |
|-------|--------|
| **Category** | Technical / Cross-Browser |
| **Likelihood** | 2 (Safari has known MediaRecorder limitations) |
| **Impact** | 3 (AI session recording fails on Safari; candidate gets no feedback) |
| **Score** | 6 — Medium |
| **Description** | `MediaRecorder` API support varies: Chrome/Firefox support `webm/vp8`, Safari supports `mp4/h264`. If encoding format is not negotiated correctly, recording fails silently or produces an unplayable file. |
| **Mitigation** | 1. Detect supported MIME types at session start (`MediaRecorder.isTypeSupported()`). 2. Record in the browser's native format; transcode to a standard format (mp4) on the server after upload. 3. Pre-session compatibility check ("Testing your browser...") verifies camera, microphone, and MediaRecorder support before the session consent dialog. 4. Show a clear error with browser recommendation if recording is not supported. |
| **Residual Risk** | Score 3 — Low |
| **Owner** | Frontend Architect |
