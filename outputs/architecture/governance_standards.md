## 1. API Design Standards

### 1.1 REST Conventions

| Rule | Standard |
|------|---------|
| URL structure | Plural nouns, kebab-case: `/api/v1/mock-sessions`, `/api/v1/question-bank` |
| HTTP verbs | GET (read), POST (create), PUT (full replace), PATCH (partial update), DELETE |
| Versioning | URI versioning: `/api/v1/...`; breaking changes require a new version |
| Response envelope | `{ data: T, meta?: PaginationMeta, error?: ApiError }` — always consistent |
| Error format | `{ error: { code: string, message: string, details?: object } }` |
| HTTP status codes | 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Validation Error, 429 Rate Limited, 500 Internal Server Error |
| Pagination | Cursor-based for large sets: `{ data: T[], meta: { next_cursor, has_more, total } }` |
| Filtering | Query params: `?type=behavioral&level=senior&industry=software` |
| Sorting | `?sort=created_at&order=desc` |

### 1.2 WebSocket Events

All WebSocket messages use the envelope:
```json
{
  "event": "score_ready",
  "payload": { "session_id": "...", "score": 82 },
  "timestamp": "2026-05-26T10:00:00Z"
}
```

Reserved event names: `connect`, `disconnect`, `error`, `ping`, `pong`

## 2. Code Standards

### 2.1 TypeScript Rules (enforced via ESLint + tsc)

- `strict: true` in all `tsconfig.json` files — no implicit `any`
- No `as unknown as X` casts without a comment explaining why
- Shared types live in `/packages/types` (monorepo) — never duplicated between frontend and backend
- All API response types are generated from OpenAPI spec (single source of truth)
- No `console.log` in production code — use the structured logger (`logger.info`, `logger.error`)

### 2.2 Naming Conventions

| Context | Convention | Example |
|---------|-----------|---------|
| Variables / functions | camelCase | `sessionScore`, `getQuestionById` |
| Classes / interfaces | PascalCase | `MockSession`, `QuestionService` |
| Constants | SCREAMING_SNAKE_CASE | `MAX_SESSION_DURATION_MS` |
| Database tables | snake_case | `mock_sessions`, `question_answers` |
| Database columns | snake_case | `created_at`, `user_id` |
| Environment variables | SCREAMING_SNAKE_CASE | `DATABASE_URL`, `CLAUDE_API_KEY` |
| React components | PascalCase | `QuestionCard`, `SessionTimer` |
| CSS classes (Tailwind) | Tailwind utilities only — no custom class names unless in `globals.css` |
| File names | kebab-case | `question-card.tsx`, `session-service.ts` |

### 2.3 Module Boundaries (Backend)

Each module follows this internal structure:
```
modules/
  session/
    session.routes.ts      ← Fastify routes (HTTP boundary)
    session.service.ts     ← Business logic (no direct DB)
    session.repository.ts  ← DB queries only (Drizzle ORM)
    session.schema.ts      ← Zod validation schemas
    session.types.ts       ← TypeScript types for this module
```

**Rules:**
- Routes → Service → Repository (one direction only)
- No module imports another module's `repository.ts` directly
- Cross-module calls go through the service interface
- No raw SQL outside `repository.ts` files

## 3. Security Standards

### 3.1 Input Validation

- **All** external inputs (request body, query params, path params, file uploads) validated with **Zod** before reaching service layer
- Fastify JSON Schema validation is a second defense layer (not a replacement for Zod)
- File uploads: validate MIME type (not just extension), enforce max size (5MB for resumes, 500MB for recordings), scan with ClamAV

### 3.2 Database Security

- Application DB user has only: SELECT, INSERT, UPDATE, DELETE on application tables
- `consent_log` and `audit_log` tables: application user has INSERT only (no UPDATE, no DELETE)
- All DB queries use **Drizzle ORM** parameterized queries — no raw string interpolation
- Database credentials rotate every 90 days via AWS Secrets Manager auto-rotation

### 3.3 Secrets Management

- Zero secrets in source code or environment files committed to git
- All secrets injected at runtime via AWS Secrets Manager
- `.env` files allowed only for local development and must be in `.gitignore`
- Pre-commit hook (`gitleaks`) blocks commits containing secrets patterns

### 3.4 API Security Checklist (enforced at PR review)

- [ ] Authentication: is the endpoint protected by JWT middleware?
- [ ] Authorization: does the handler check the caller's role before accessing data?
- [ ] Rate limiting: is the endpoint covered by the global rate limiter (or a custom limit)?
- [ ] Input validation: is every input validated with Zod schema?
- [ ] Output: does the response exclude any fields that shouldn't be exposed (e.g., password hashes, internal IDs)?
- [ ] Logging: are errors logged without PII (no email addresses or user content in error logs)?

## 4. Data Privacy Standards

### 4.1 PII Classification

| Data Type | Classification | Storage Rule |
|-----------|---------------|-------------|
| Email address | PII | Encrypted at rest (pgcrypto) |
| Full name | PII | Encrypted at rest |
| Resume content | Sensitive PII | Encrypted S3 object; deleted with account |
| Session recording (video/audio) | Sensitive PII | Encrypted S3; auto-delete after 90 days |
| STT transcript | Sensitive PII | Encrypted DB field; auto-delete after 90 days |
| AI score (numeric) | Non-PII | Standard storage |
| Rubric scores | Non-PII | Standard storage |
| IP address (in logs) | PII | Retained max 30 days; not written to application logs |

### 4.2 Data Retention Automation

A nightly cron job (`retention-cleanup`) runs at 02:00 UTC:
1. Delete S3 objects for sessions older than 90 days (or user-set custom retention)
2. Delete STT transcripts from DB older than 90 days
3. Process pending account deletion requests (delete all PII within 30 days of request)
4. Write a deletion summary to the `audit_log` table

### 4.3 Consent Requirements

- Consent must be obtained before any recording begins (AI session or live session)
- Consent dialog must explicitly state: what is being recorded, how long it will be retained, and how to delete it
- Consent is logged in `consent_log` with: `user_id`, `session_id`, `type` (ai_session | live_session), `accepted_at`, `ip_address`, `user_agent`
- Declining consent cancels the session — no partial recording is permitted

## 5. Accessibility Standards

- All frontend PRs must pass `axe-core` automated scan with zero critical or serious violations before merge
- Every interactive component must have a visible focus indicator (not `outline: none` without replacement)
- All `<img>` elements must have descriptive `alt` text (empty `alt=""` for decorative images)
- All form fields must have an associated `<label>` (not just placeholder text)
- All video content must have captions within 48 hours of publishing
- Color alone must not convey meaning — always pair with text, icon, or pattern
- ARIA attributes are a last resort — use semantic HTML first (`<button>`, `<nav>`, `<main>`, `<section>`)

## 6. Testing Standards

|-----------|------|--------------------|---------|
| Unit tests | Vitest | ≥ 80% line coverage on service and repository layers | On every push |
| Component tests | Vitest + React Testing Library | All interactive components | On every push |
| API integration tests | Vitest + Supertest | All REST endpoints with auth + validation scenarios | On every push |

| Load tests | k6 | 500 concurrent sessions; p95 ≤ 3s | Before each release |
| Security scan | npm audit + Snyk | Zero critical vulnerabilities | On every push (blocks merge if critical) |

## 7. CI/CD Standards

### 7.1 Branch Strategy

```
main         ← production-ready; protected; requires PR + 1 review + all checks green
staging      ← auto-deployed to staging environment on merge
feature/*    ← developer branches; merge to staging via PR
hotfix/*     ← emergency fixes; merge directly to main + backport to staging
```

### 7.2 Pipeline Gates (all must pass before merge to main)

1. TypeScript compile — zero errors
2. ESLint — zero errors, zero warnings
3. Unit + integration tests — all pass, coverage ≥ 80%
4. Dependency vulnerability scan — zero critical CVEs
5. Secret scan (gitleaks) — no secrets detected
6. Docker build — image builds successfully
7. Staging deployment — smoke test passes

### 7.3 Deployment Strategy

- **Staging:** Auto-deploy on every merge to `staging` branch
- **Production:** Manual trigger (one-click) after all gates pass; blue-green deployment via ECS
- **Rollback:** Previous ECS task definition re-activated within 2 minutes if health check fails post-deploy
- **Feature flags:** New Phase 2 features deployed behind flags; enabled per-environment without a code deploy

## 8. Observability Standards

### 8.1 Structured Log Format

Every log line must include:
```json
{
  "level": "info",
  "timestamp": "2026-05-26T10:00:00Z",
  "service": "session-service",
  "correlation_id": "req-abc123",
  "user_id": "usr-xyz",
  "message": "AI session completed",
  "duration_ms": 420
}
```

**Prohibited in logs:** email addresses, full names, resume content, transcript text, recording URLs

### 8.2 Required Metrics (emit from all services)

- `http_request_duration_ms` (histogram, labeled by route + status code)
- `job_queue_depth` (gauge, labeled by queue name)
- `stt_processing_duration_ms` (histogram)
- `ai_score_generation_duration_ms` (histogram)
- `webrtc_session_active_count` (gauge)
- `error_rate` (counter, labeled by service + error type)

### 8.3 Alerting Thresholds

| Alert | Threshold | Severity |
|-------|----------|---------|
| API error rate | > 1% over 5 minutes | P1 — page on-call |
| STT queue depth | > 50 jobs | P2 — Slack alert |
| Score report latency (p95) | > 90 seconds | P2 — Slack alert |
| Platform uptime | < 99.5% monthly | P1 — page on-call |
| Active WebRTC sessions drop | > 20% in 2 minutes | P1 — page on-call |
| Failed login rate | > 50/minute per IP | P2 — security alert |
