## P0 — Critical

### DEF-001: Refresh Token Stored in localStorage — XSS Vulnerability
- **File:** [outputs/implementation/frontend/lib/api/client.ts](../implementation/frontend/lib/api/client.ts) — Line 15, 59
- **Description:** The `access_token` is stored in `localStorage` (`localStorage.setItem('access_token', ...)`). This exposes the token to any JavaScript running on the page (XSS attack). An attacker injecting script can steal the token and impersonate the user indefinitely.
- **Expected:** Access tokens should be stored in memory only (JS variable / React state). Refresh tokens are already correctly set as `HttpOnly` cookies by the backend. The frontend should not persist tokens to localStorage.
- **Fix:** Remove all `localStorage.setItem/getItem` for tokens. Store `access_token` in a module-level variable or React context. On page reload, call `POST /auth/refresh` (the HttpOnly cookie is sent automatically) to get a new access token silently.
- **Assigned to:** `frontend_developer_agent`
- **Severity Rationale:** Token theft via XSS enables full account takeover. OWASP A07:2021.

## P1 — High

### DEF-002: No CSRF Protection on Cookie-Based Auth Endpoints
- **File:** [outputs/implementation/backend/modules/auth/auth.service.ts](../implementation/backend/modules/auth/auth.service.ts) — refresh token flow
- **Description:** The refresh token is stored in a `SameSite=Strict` cookie (correct), but the API contract does not specify a CSRF token requirement for state-mutating endpoints that rely on the cookie. On older browser versions where `SameSite` is not enforced, CSRF attacks are possible on `POST /auth/refresh` and `POST /auth/logout`.
- **Fix:** Add `fastify-csrf-protection` plugin to all routes that accept cookie-based auth. Issue a CSRF token on login, validate on all non-GET requests.
- **Assigned to:** `backend_developer_agent`

### DEF-003: `docker-compose.yml` Hardcodes DB Password in Plain Text
- **File:** [outputs/implementation/devops/docker-compose.yml](../implementation/devops/docker-compose.yml) — Line 33
- **Description:** `POSTGRES_PASSWORD: app_password` is hardcoded. While this is a local dev file, developers may inadvertently copy this pattern to staging config or commit `.env` files with real passwords.
- **Fix:** Replace with `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-app_password}` to allow environment override. Add `docker-compose.yml` to the secrets-scan exclusion list with a comment explaining it is dev-only. Add a `SECURITY.md` note warning never to use these credentials outside local dev.
- **Assigned to:** `devops_developer_agent`

### DEF-004: Whisper Mock Server (`whisper-mock.js`) Not Provided
- **File:** [outputs/implementation/devops/docker-compose.yml](../implementation/devops/docker-compose.yml) — Line 66
- **Description:** The Docker Compose file mounts `./whisper-mock.js` but this file does not exist in the implementation output. The worker service depends on the Whisper endpoint being available. Local development will fail to start with a mount error.
- **Fix:** Create `outputs/implementation/devops/whisper-mock.js` — a minimal Node.js HTTP server that accepts `POST /transcribe` and returns a dummy transcript JSON. Also create `outputs/implementation/devops/localstack-init.sh` to create the required S3 buckets on LocalStack startup.
- **Assigned to:** `devops_developer_agent`

## P2 — Medium

### DEF-005: `encryptField()` in auth.service.ts Is a No-Op
- **File:** [outputs/implementation/backend/modules/auth/auth.service.ts](../implementation/backend/modules/auth/auth.service.ts) — Lines 93–97
- **Description:** The comment states "actual encryption is done at DB layer" but the implementation just wraps the value in `Buffer.from(value)` with no actual encryption. If the DB layer does not handle pgcrypto encryption transparently, PII (email, full name) will be stored as plaintext bytes — violating NFR-SEC-02 and GDPR.
- **Fix:** Either: (a) implement application-level AES-256-GCM encryption using `crypto.createCipheriv` before storing, or (b) use pgcrypto `pgp_sym_encrypt()` as a DB function called via Drizzle raw SQL. Document the chosen approach clearly.
- **Assigned to:** `backend_developer_agent`

### DEF-006: API Client Does Not Handle Multipart Upload Auth Header Correctly
- **File:** [outputs/implementation/frontend/lib/api/client.ts](../implementation/frontend/lib/api/client.ts) — Lines 117–126
- **Description:** For `uploadResponse()`, the code sets `headers: {}` to let the browser set `Content-Type` with boundary — correct. But the spread in the base `request()` function then applies `'Content-Type': 'application/json'` **after** the override, clobbering the multipart header. The upload will send `Content-Type: application/json` and the server will reject it.
- **Fix:** In the base `request()` function, only set `Content-Type: application/json` if `options.body` is a string, not a `FormData`. Check `options.body instanceof FormData` and skip the Content-Type header in that case.
- **Assigned to:** `frontend_developer_agent`

### DEF-007: E2E Tests Lack `playwright.config.ts` — Cannot Run Standalone
- **File:** [outputs/qa/tests/e2e/candidate-journey.spec.ts](tests/e2e/candidate-journey.spec.ts)
- **Description:** The E2E test file references `process.env.PLAYWRIGHT_BASE_URL` and uses `@axe-core/playwright` but no `playwright.config.ts` is provided. Without it, browser configuration, timeouts, retry counts, and video recording on failure cannot be configured. Tests will run with defaults only.
- **Fix:** Create `outputs/qa/tests/playwright.config.ts` with: project definitions (Chromium, Firefox, WebKit), 30s timeout, 2 retries on CI, video `on-first-retry`, screenshot `only-on-failure`, and `baseURL` from env.
- **Assigned to:** `qa_developer_agent`

### DEF-008: No Database Migration Runner / Script Defined
- **File:** [outputs/implementation/database/migrations/](../implementation/database/migrations/)
- **Description:** Two migration SQL files exist but no migration runner (e.g., `migrate.ts` using Drizzle migrate, or a shell script calling `psql`) is provided. Without this, developers have no automated way to apply migrations in order, and CI cannot run them before integration tests.
- **Fix:** Add `outputs/implementation/database/migrate.ts` using Drizzle's `migrate()` function, or a `npm run db:migrate` script that applies files in numeric order via `psql`.
- **Assigned to:** `db_developer_agent`

## P3 — Low

### DEF-009: `ConsentDialog` Missing `data-testid` Attributes for E2E Tests
- **File:** [outputs/implementation/frontend/components/session/ConsentDialog.tsx](../implementation/frontend/components/session/ConsentDialog.tsx)
- **Description:** The E2E tests locate elements via `getByRole('dialog', { name: /consent/i })` and `getByRole('checkbox', { name: /i have read/i })`. The dialog `aria-label` and checkbox `Label` text must match exactly. Currently the `DialogTitle` text and `Label` text are slightly different from what the tests expect.
- **Fix:** Align the `DialogTitle` and `Label` text with the E2E test selectors, or add `data-testid` attributes to the key elements (`data-testid="consent-dialog"`, `data-testid="consent-checkbox"`).
- **Assigned to:** `frontend_developer_agent`

### DEF-010: Scoring Unit Tests Use `unknown` Cast Anti-Pattern
- **File:** [outputs/qa/tests/unit/scoring.service.test.ts](tests/unit/scoring.service.test.ts)
- **Description:** Multiple lines use `mockDb.update.mock.calls[0]` to inspect captured values, but the mock chain intercepts the `set()` call, not `update()`. The captured values check on `mockDb.update.mock.calls[0]` will always be `undefined`. The intent is correct but the assertion target is wrong.
- **Fix:** Refactor the capture pattern to intercept `set()` via `mockImplementation`, as done in the `filler word detection` describe block. Apply consistently across all `scoring.service.test.ts` assertions.
- **Assigned to:** `qa_developer_agent`

### DEF-011: `use-session-recording.ts` Does Not Stop Tracks on `reset()` if Still in `requesting_permissions` State
- **File:** [outputs/implementation/frontend/hooks/use-session-recording.ts](../implementation/frontend/hooks/use-session-recording.ts) — Line 96
- **Description:** If the user calls `reset()` while the `requestPermissions()` promise is still in flight (state = `requesting_permissions`), the promise resolves after reset and sets `streamRef.current`. The stream is then never released, leaving the camera indicator light on indefinitely.
- **Fix:** Add an `abortedRef` flag that is set to `true` in `reset()`. In `requestPermissions()`, after `getUserMedia` resolves, check if `abortedRef.current === true` — if so, immediately stop all tracks and return `false`.
- **Assigned to:** `frontend_developer_agent`
