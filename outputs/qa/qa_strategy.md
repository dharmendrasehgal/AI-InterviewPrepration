## 1. QA Mission

Ensure every release meets functional correctness, security compliance, accessibility standards, and performance targets defined in the NFR document — before any user is exposed to it. QA is a gate, not a checkpoint.

---

## 2. Test Pyramid

```
                    ┌────────────────────┐
                    │    E2E Tests       │  ~10% of suite
                    │  (Playwright)      │  Golden paths only
                    ├────────────────────┤
                    │  Integration Tests │  ~30% of suite
                    │  (Supertest + DB)  │  All API endpoints
                    ├────────────────────┤
                    │    Unit Tests      │  ~60% of suite
                    │   (Vitest)         │  All service & util logic
                    └────────────────────┘

Specialised suites (run on PR to main):
  ┌─────────────────────┐  ┌──────────────────────┐  ┌─────────────────────┐
  │  Accessibility      │  │  Security (SAST)     │  │  Performance        │
  │  axe-core/Playwright│  │  npm audit + Snyk    │  │  k6 load tests      │
  └─────────────────────┘  └──────────────────────┘  └─────────────────────┘
```

## 3. Coverage Targets

| Layer | Tool | Minimum Coverage | Blocking? |
|-------|------|-----------------|-----------|
| Unit — service layer | Vitest | ≥ 80% line coverage | Yes — blocks merge |
| Unit — repository layer | Vitest | ≥ 80% line coverage | Yes — blocks merge |
| API Integration | Supertest | 100% of documented endpoints | Yes — blocks merge |
| E2E — golden paths | Playwright | All US-01 → US-15 happy paths | Yes — blocks release |
| E2E — critical error paths | Playwright | Auth failure, recording failure, payment error | Yes — blocks release |
| Accessibility | axe-core | 0 critical/serious violations | Yes — blocks merge |
| Security | npm audit | 0 critical CVEs | Yes — blocks merge |
| Load | k6 | p95 ≤ 3s at 500 concurrent sessions | Yes — blocks GA release |

## 4. Test Environments

| Environment | Purpose | Data | Reset Cadence |
|-------------|---------|------|---------------|
| **Local** (`docker compose`) | Developer testing | Seeded fixtures | On demand |
| **CI** (GitHub Actions) | Automated unit + integration | Ephemeral per run | Every run |
| **Staging** | E2E, accessibility, load | Anonymised prod-like seed | Weekly reset |
| **Production** | Smoke tests only post-deploy | Real data | Never reset |

Staging data rules:
- No real user PII — all emails are `testuser+{n}@platform-test.com`
- Recording fixtures are synthetic (pre-recorded MP4 test files, not real sessions)
- 200 seeded questions matching production seed

## 5. Test Types & Ownership

### 5.1 Unit Tests (Vitest)
- **Owned by:** Backend / Frontend developers
- **Scope:** All service methods, utility functions, React hooks, scoring algorithms
- **Run:** On every push to any branch
- **Standard:** Each public method has at least one happy-path and one error-path test
- **Mocking policy:** Mock only external I/O (DB, S3, Claude API, STT) — never mock internal business logic

### 5.2 API Integration Tests (Vitest + Supertest)
- **Owned by:** QA Developer + Backend Developer
- **Scope:** Every endpoint in `api_contracts.md` — request validation, response shape, auth enforcement, rate limiting
- **Run:** On every push; requires running PostgreSQL + Redis (provided by CI services)
- **Test DB:** Uses a separate `interviewprep_test` database; migrations run before suite, rolled back after

### 5.3 E2E Tests (Playwright)
- **Owned by:** QA Developer
- **Scope:** All 15 user stories' happy paths + critical failure modes
- **Run:** On PR to `main` and pre-release
- **Browsers:** Chromium (required), Firefox (required), WebKit/Safari (required for MediaRecorder compatibility)
- **Recording:** All failed test runs save a video recording and screenshot for debugging

### 5.4 Accessibility Tests (axe-core via Playwright)
- **Owned by:** QA Developer + Frontend Developer
- **Scope:** Every page route in the application
- **Run:** On PR to `main`
- **Standard:** Zero critical or serious axe-core violations — warnings are tracked but not blocking
- **Manual audit:** Full manual WCAG 2.1 AA audit by a specialist before each major release

### 5.5 Security Tests
- **Owned by:** DevOps + QA Lead
- **Automated:** `npm audit` (every push), Snyk scan (weekly), gitleaks (every commit)
- **Manual:** External penetration test before Phase 1 GA and Phase 2 GA
- **Pen test scope:** OWASP Top 10, WebRTC session hijacking, recording consent bypass, JWT tampering

### 5.6 Performance / Load Tests (k6)
- **Owned by:** QA Developer + DevOps
- **Scenarios:**
  - `load_question_bank.js` — 1,000 concurrent browsing users, 5-min sustained
  - `load_ai_sessions.js` — 500 concurrent AI mock sessions (recording upload + scoring queue)
  - `load_search.js` — 200 concurrent search queries with autocomplete
- **Run:** Before every Release Gate (Alpha, Beta, GA)
- **Acceptance:** p95 response time ≤ 3s for all scenarios; error rate < 0.1%

## 6. Defect Management

### 6.1 Severity Classification

| Severity | Definition | SLA to Fix | Example |
|----------|-----------|-----------|---------|
| **P0 — Critical** | Data loss, security breach, complete feature unavailability | Fix before next deploy | Recording stored without consent; auth bypass |
| **P1 — High** | Core feature broken for all users | Fix within 24h | AI session fails to start; score report not generated |
| **P2 — Medium** | Feature degraded or broken for subset of users | Fix within current sprint | Safari recording fails; search autocomplete broken |
| **P3 — Low** | Minor UX issue, cosmetic, non-blocking | Fix in next sprint | Tooltip misaligned; incorrect placeholder text |

### 6.2 Defect Lifecycle

```
Open → Assigned → In Progress → Fixed → Verification → Closed
                                              │
                                         (Fail → Reopened)
```

### 6.3 Defect Triage Cadence
- **Daily:** P0 and P1 defects reviewed by QA Lead + Product Manager
- **Sprint Review:** All open P2 and P3 defects reviewed for prioritisation
- **Release Gate:** Zero P0/P1 defects permitted; P2 requires QA Lead sign-off to proceed

## 7. Release Quality Gates

### Alpha Gate (end of Sprint 4)
- [ ] Zero P0 defects
- [ ] Unit test coverage ≥ 80% on Auth, Session, and Scoring modules
- [ ] All API integration tests passing for: `/auth`, `/users`, `/mock-sessions`
- [ ] Consent flow tested: recording cannot begin without DB consent record
- [ ] MediaRecorder compatibility verified: Chrome, Firefox, Safari

### Closed Beta Gate (end of Sprint 5)
- [ ] Zero P0/P1 defects
- [ ] All unit + integration tests passing
- [ ] E2E suite (US-01 through US-10) passing on Chromium + Firefox
- [ ] axe-core: zero critical violations on Dashboard, Session, Score Report, Archive
- [ ] Score report latency p95 ≤ 60s (verified against staging)
- [ ] STT transcription accuracy ≥ 80% on 20 test recordings

### GA Gate (end of Sprint 6)
- [ ] Zero P0/P1 defects; all P2 defects have QA Lead sign-off
- [ ] All test suites passing (unit, integration, E2E, accessibility)
- [ ] External penetration test complete; zero critical findings open
- [ ] Load test passed: 500 concurrent AI sessions, p95 ≤ 3s
- [ ] Manual WCAG 2.1 AA audit complete; zero Level A or AA failures
- [ ] GDPR compliance checklist signed off by legal

## 8. Regression Strategy

- **Full regression:** Run before every release (automated suite takes ~25 min on CI)
- **Smoke regression:** Run post every production deployment (< 5 min — 10 critical path tests)
- **Flaky test policy:** Any test that fails non-deterministically 3 times in 7 days is quarantined, tagged `@flaky`, and assigned for immediate investigation
- **Regression baseline:** Maintained in `tests/e2e/smoke/` — these tests are never skipped
